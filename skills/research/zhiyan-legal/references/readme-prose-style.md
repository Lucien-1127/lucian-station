# README 與對外文件 — 寫作風格規範

> 2026-06-27 根據使用者反饋建立：
> - 「輸出不要過度工程語言」
> - 「用繁體中文命名」
> - README 應使用 WRITER prose 風格

## 核心原則

1. **繁體中文優先** — 所有對外文件先寫繁體中文，英文次之。中英文都提供時，中文展開（open by default），英文摺疊（collapsed）。
2. **prose 為主** — 用自然段落敘述，不要一開頭就丟表格或 code block。先說故事，再說規格。
3. **工程語言最小化** — 避免「狀態機」、「路由引擎」、「參數化」、「實例化」等工程行話，改用自然詞彙。例如「狀態機」→「流程檢查」。
4. **人味開場** — 用一個具體情境或問題開頭，讓讀者知道為什麼這東西重要，而不是直接列功能清單。
5. **讀者不需要知道的東西就不寫** — API 供應商列表、儲存庫結構樹等對一般讀者無用的資訊可以省略。

## 格式選擇指南

| 想呈現的資訊 | 用什麼格式 |
|:------------|:-----------|
| 系統怎麼運作（流程） | 一段 prose，必要時用簡單的 `code` 區塊示意 |
| 功能清單 | 自然段落，不要用表格列舉 |
| 程式碼範例 | `code block` 沒問題 — 這是真的需要結構的地方 |
| 對照/比較 | 可用精簡表格，但不要超過 3 欄 |
| 版本/授權/引用 | 維持標準 bibtex / badge 格式不變 |

## 反例 vs 正例

| ❌ 工程味 | ✅ 人味 prose |
|:----------|:--------------|
| 「系統採用七層幻覺防禦架構，包含 SRP 安全路由協議與核心閘門事實分級機制」 | 「一條錯誤的法條引用可能讓當事人失去自由。智研就是把這種傷害降到最低的系統。」 |
| 「RQ1: Does a no-fabrication citation policy reduce hallucinated statutes? Mitigation: Citation Policy v2.1. Measured by: fabrication rate vs. baseline」 | 「三個核心問題貫穿整個系統。第一，強制引用能不能真的減少捏造法條？」 |
| 表格 + code block 佔滿畫面 | prose 為主，適度穿插結構化元素 |
